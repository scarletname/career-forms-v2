## 1. Describe

В задании есть две основные проблемы, которые необходимо решить:

- Менеджеры зависят от разработчиков при создании и изменении форм.
- Студенты бросают заполнение форм, поэтому важно обеспечить удобный процесс заполнения и возможность анализировать причины отказа.

Главный пользователь системы - менеджер, студент - пользователь публичной формы. Менеджер должен получить возможность самостоятельно управлять формами, а удобство студента и аналитика необходимы для снижения количества незавершённых заявок.

## 2. Do / Not to do
Do:
* Создание и редактирование форм. Менеджер может создать форму, добавить и удалить поля, изменить их порядок, указать обязательность и настроить варианты ответов.
* Ограниченное число типов полей:

    | Тип | Назначение | 
    |----|----|
    | Короткий текст | ФИО, название проекта |
    | Длинный текст | ответ на открытые вопросы, сопроводительное письмо |
    | Email | контактные данные |
    | Дата | для возраста или записи на звонок |
    | Один вариант | выбор направления или формата участия |
    | Несколько вариантов | выбор нескольких интересующих направлений |

* Публикация по уникальной ссылке. До первой публикации менеджер может посмотреть форму в режиме превью по адресу /f/<id>?preview. В превью доступны черновики, отображается предупреждение, отправка ответов и сбор аналитики отключены.
* Валидация. Проверка обязательных полей, формата email, даты и корректности ответов выполняется только на сервере после нажатия кнопки «Отправить». Ошибки отображаются рядом с соответствующими полями. При неудачной отправке введённые данные сохраняются в локальном черновике.
* Управление опубликованной формой. Менеджер может исправить опечатку или закрыть приём заявок. При редактировании формы, прошлые ответы остаются. Необходимо сохранять вместе с каждым ответом снимок вопроса и его значения на момент отправки.
* Просмотр ответов. Менеджер видит список заявок и может открыть каждую отдельно.
* Базовая аналитика. Количество открытий формы, начатых заполнений и отправленных заявок, а также примерное место, на котором студенты прекращают заполнение.

    | Что считаем? | Как считаем? | 
    |----|----|
    | открытие | первый заход с этим sessionId |
    | начало | первое изменение любого поля |
    | отправка | успешный submit |
    | место ухода | для начатых, но не отправленных сессий берём последнее поле, на котором был фокус, и считаем такие сессии по каждому полю |

* Обработка персональных данных. Для MVP отобразить галочку для согласия с обработкой персональных данных. В реальном проекте необходимо указать ссылку на положение о хранении персональных данных.
* Проверка данных на сервере. Сервер самостоятельно проверяет типы полей, длину текстов и наличие вариантов ответов.
* Ограничения формы. Максимум 50 вопросов и 30 вариантов ответа для одного вопроса. Также устанавливаются ограничения на длину текстов.
* Сохранение идентификаторов. При редактировании формы ID существующих полей и вариантов сохраняются. Это необходимо для корректной работы аналитики и порядка полей.
* Удобство заполнения. Размер шрифта в полях ввода 16px, чтобы избежать автоматического увеличения страницы при фокусе на поле ввода в Safari на iPhone.

Not to do:
- Добавление других типов полей. Каждый дополнительный тип требует отдельной реализации отображения, валидации и обработки, их можно добавить уже в реальный проект.
- Авторизация и разграничение прав. По условию админка должна быть доступна без авторизации. Поэтому полноценную систему пользователей и ролей не реализую. В реальном сервисе необходима доработка.
- Загрузка файлов. Она требует ограничений по размеру и формату, безопасного хранения и обработки загруженных данных.
- Сложная аналитика и индивидуальные рекомендации. Для первой версии достаточно базовой воронки заполнения и статистики по прекращению заполнения формы.
- Сохранение черновиков на сервере и синхронизация между устройствами. Для MVP достаточно локального сохранения в браузере.
- Экспорт в несколько форматов и расширенная отчётность. Сначала достаточно просмотра ответов в админке. CSV можно добавить в дальнейшем.
- Сложная система версий форм. Не буду реализовывать историю изменений и восстановление предыдущих версий. При этом уже отправленные ответы должны сохраняться, а редактирование формы не должно приводить к их потере или неправильному отображению.
- Интеграции с внешними сервисами. Требуется автономный запуск без API-ключей и дополнительных сервисов.
- Удаление форм. Для MVP достаточно возможности закрыть приём заявок.

## Assumptions
- Изменения опубликованной формы. Изменения сразу становятся видны студентам. Если студент открыл форму до изменения, сервер при отправке проверяет ответы по актуальной схеме. Ответы на удалённые поля игнорируются, а новые обязательные поля требуют заполнения. Это может привести к необходимости повторно проверить форму перед отправкой.
- Удаление полей. Старые ответы сохраняются вместе со снимком вопросов на момент отправки. Поэтому удаление поля не приводит к потере ранее полученных ответов. При этом статистика по удалённому полю больше не отображается.
- Идентификатор формы. Для каждой формы генерируется случайный уникальный идентификатор, который используется в ссылке для заполнения. Это затрудняет угадывание ссылок, но делает их менее удобными для запоминания.
- Подсчёт открытий. Один браузер считается одним посетителем в рамках сессии. Для этого используется `sessionId`. При открытии формы в другом браузере или режиме инкогнито создаётся новая сессия. Поэтому статистика по открытиям и количеству посетителей является приблизительной.
- Синхронная запись. Два студента, отправивших заявки одновременно, не затрут друг друга. Node.js выполняет JavaScript в одном потоке, поэтому синхронная функция записи не может быть прервана другим запросом посередине выполнения. Минус: на время записи сервер не обрабатывает другие запросы. При размере файла в сотни килобайт задержка должна быть небольшой.
- Обновление данных. При обновлении данные сначала изменяются в памяти, а затем записываются на диск. Если запись завершится ошибкой, данные в памяти и JSON-файле могут различаться.
- Варианты ответов. Для вопросов с выбором необходимо указать минимум два варианта. Повторяющиеся варианты запрещены.
- Идентификаторы полей и вариантов. Конструктор передаёт серверу ID существующих элементов при сохранении. Сервер проверяет их формат и отсутствие повторов. Если ID некорректный или повторяется, генерируется новый.
- Жизненный цикл формы. Форма может переходить между статусами `черновик → опубликована → закрыта → опубликована`. Закрыть черновик или вернуть опубликованную форму в черновик нельзя, так как ссылка уже может быть у студентов.
- Публикация формы. Нельзя опубликовать форму без вопросов. Также нельзя удалить последний вопрос у уже опубликованной формы.
- Сохранение черновика. Черновик сохраняется только при условии, что форма прошла проверку и содержит обязательные данные, например название. Ошибки отображаются сразу, а не в момент публикации.
- Согласие на обработку данных. Отметка о согласии не сохраняется в локальном черновике. При каждой отправке студент должен самостоятельно поставить галочку.
- Изменение формы во время заполнения. Если организатор изменил форму, а сервер вернул ошибку для поля, которого уже нет на открытой странице, студенту предлагается обновить страницу. Перед обновлением введённые ответы сохраняются в локальном черновике.
- Работа без localStorage. Если браузер не поддерживает или блокирует localStorage, форма продолжает работать без сохранения черновика и сбора аналитики.
- Генерация идентификаторов сессий. Если crypto.randomUUID недоступен, например при открытии формы с телефона по локальному IP-адресу через HTTP, используется запасной генератор идентификаторов.

## Stack
**Node.js 20+** - условие задания
**Express** - сам разбирает адреса страниц, читает JSON из запросов и отдаёт файлы
**JavaScript без сборки** - для конструктора форм JS нужен в любом случае, а для проекта лучше использовать один подход. Сборка - лишний шаг, который может сломаться при запуске на другом устройстве
**Хранение в JSON-файле** - для сокращения объема реализации
**Безопасная запись JSON** - данные сначала записываются во временный файл, затем заменяют основной через rename, чтобы снизить риск повреждения данных при сбое
**Серверная валидация** - сервер повторно проверяет ответы по схеме формы, так как проверки в браузере можно обойти
**Защита от XSS** - вопросы и ответы выводятся через textContent, что предотвращает выполнение внедрённых скриптов как в публичной форме, так и в админке при просмотре ответов

Запуск строго через `npm install && npm start`, без внешних сервисов.
